## Findings considered and rejected

- **Extracting a shared hunter-pick "gate" used by both resolutions (001):** rejected — two independent ~15-line pause mechanisms are simpler than a premature abstraction; revisit if a third pause point appears (= 009 now adds timeouts to both).
- **`isHunterInLove()` overwriting an existing queue entry's cause, and `killHunterRevenge()` killing immediately while also queueing (001):** these are known quirks pinned by existing tests; the double-kill aspect is now fixed by 008 (skip already-dead players in `processPendingDeaths` pass 2). The cause-overwrite quirk (`isHunterInLove` overwrites `WEREWOLVES` with `PARTNER_SUICIDE` if the lover was already queued) is NOT fixed by any current plan — it's a behavior change that needs its own plan and dedicated tests; flagged here so it's not re-audited as novel.
- **`processPendingDeaths` two-pass iteration mutation safety:** confirmed safe — iteration is over snapshot arrays, not the live Map; not a finding.
- **`submitHunterPick` OR fallthrough between day-vote and night-dawn:** confirmed by design — phases are sequential; not a finding.
- **4-player role distribution math:** role-balance design decision, not a bug; not a finding.
- **`sound-play` spawning `afplay` via `exec`:** async, not event-loop-blocking; not a finding.
- **Dashboard's one-socket-per-mock-player (`mock-players.ts:82`):** acceptable for dev tooling; flagged as perf-02 in the audit but no plan written (Secondary priority — single multiplexed socket would need client-side changes to mock-player semantics; deferred).
- **Broadcast via Socket.io rooms instead of per-socket loops (`broadcastWerewolfVotes`, `alertPlayersOfRoles`):** audit perf-03; the werewolf N is ≤ 2 today so the win is small. Deferred — a future perf plan can introduce `socket.join('werewolves')` on role assignment.
- **Dead/duplicate `Effect-pair` socket-handler system (plain vs Effect):** the entire duplicate was not given its own delete plan; the audit's tech-debt-08 captures it, but `socket-event-router.effect.ts` / `event-handlers.effect.ts` are the future home of the migrated handlers per the documented Effect migration strategy. Deleting now would cost work that's about to be repurposed. Plans 013 (reconcile Tags) and 014 (fix dead handler ref) surgically fix the most dangerous pieces without the broader delete.

## How to execute

1. Each plan lives at `plans/NNN-<slug>.md`; an executor subagent reads a single plan file fresh and follows it (see plan 001's executor-instructions block for the convention every plan follows).
2. The advisor dispatches executors one at a time per the dependency order above (P1 first, then P2, then P3); approves via the `execute <plan>` flow (= references/closing-the-loop.md in this skill's directory).
3. Merging to `main` is the user's call — executors only commit to the `advisor/NNN-<slug>` branch in their isolated worktree; the advisor never merges or pushes.
4. When a plan is DONE, the executor updates its row in this index; if BLOCKED, executor stops per STOP conditions and the advisor either rewrites the plan in place (same number if approach holds) or marks it REJECTED with one line.
